# ADR 0000: 产品需求与架构方向

## 状态

已批准

## 日期

2026-05-06

## 决策人

[用户]

---

## 1. 背景

思忆集项目已从原型阶段进入产品收口阶段。当前代码库覆盖了大量功能模块（UI、AI、服务层、同步、后端等），但缺少一份从需求出发、统摄架构方向的基线文档。此 ADR 作为未来所有 ADR 的根文档，固定产品需求、用户画像、功能优先级和架构约束。

## 2. 决策

### 2.1 目标用户

**唯一真实用户：项目创建者本人。**

画像：
- 技术能力强的个人用户
- 有自己散落的文件、笔记、任务、书签
- 需要 AI 帮助整理信息、管理文件、执行任务
- 重视数据隐私，不愿意所有数据上云
- 日常在 PC 前工作，离座时希望手机也能接住信息
- 对工具链有控制欲，不接受黑盒系统

**当前不做：** 泛化用户、多租户、企业版。

### 2.2 产品定位

> **思忆集是双端协作的个人 AI 管家 + 第二大脑。**
> 桌面端做重型工作台和深度任务，手机端做随身伴侣。
> 手机和 PC 同步上线，数据归属本地。

### 2.3 产品角色

| 角色 | 职责 | 必须满足的条件 |
|------|------|---------------|
| **管家** | 理解目标、编排能力、执行任务、主动提醒 | 能对话、能调用工具、能在有限授权下执行 |
| **第二大脑** | 全量记忆、个人知识库、偏好画像 | 能记录、能提取、能检索、能自动整理 |
| **收件箱** | 统一收口个人动态 | 浏览器/手动/语音输入→统一入口 |
| **整理器** | 将散落信息分类、标记、关联 | 行为日志自动整理+结构化提取 |
| **执行器** | 在明确授权下执行文件管理等受控动作 | 有限授权体系+审计日志 |

### 2.4 关键决策记录

#### QC-1: 管家执行边界 — 有限授权

**选择：B — 有限授权**

含义：
- AI 在用户一键授权后，可读写指定目录的文件
- 系统级操作（安装软件、修改系统配置、执行脚本）需逐次确认
- 不存在「完全自治」或「每次都问」两个极端

架构影响：
- 需要基本的**权限矩阵**（指定目录白名单 + 操作类型分类）
- 需要**审计日志**（谁、什么时间、做了什么），优先级 P1
- 不需要**回滚机制**（P2）
- `AutonomousAssistantManager` 的安全部分可以简化

#### QC-2: 第二大脑记忆颗粒度 — 全量记忆

**选择：C — 全量记忆**

含义：
- 记录对话历史
- 自动从对话中提取关键信息并结构化存储
- 记录行为日志：文件操作、浏览器访问、App 使用
- 行为日志原始数据保留 **6 个月**
- 超过 6 个月的原始日志自动归档/清理，只保留提取后的结构化事实和向量索引

空间估算（3 年）：

| 数据类型 | 3 年预估值 |
|---------|-----------|
| 对话记录 | 10 MB |
| 提取的事实（结构化） | 1 GB |
| 行为日志原始记录（6 个月滚动） | ~2 GB |
| 向量嵌入（ChromaDB） | 7 GB |
| 本地知识库索引 | 3 GB |
| 其他（缓存、配置等） | 1 GB |
| **合计** | **~14 GB** |

结论：3 年占用约 14 GB（受 6 个月原始日志滚动策略约束），远小于典型 D 盘容量（256 GB+）。**不会出现空间不足。**

架构影响：
- `memory/extractor.py` 需要从「仅对话提取」扩展为「对话+行为日志提取」
- 新增**行为日志采集层**（P0），覆盖文件监控、浏览器桥接、App 状态
- 新增**日志归档策略**（P1），6 个月自动清理原始日志
- `memory/search.py` 需要按时间分片以保持检索性能
- 隐私约束：行为日志不得外送第三方模型，这是 QC-1 的延伸

#### QC-3: 手机端优先级 — 同步上线

**选择：C — 手机端和 PC 端同步上线**

含义：
- 手机伴侣不是「以后再加」，而是 P0 功能
- 手机端最小能力：对话、收件、查记忆、接收通知
- 跨端同步不是「可有可无的增强」，而是 P0 基础设施

架构影响：
- `domain/models/`（实体契约）从「未来规划」升级为 **P0**——同步的前提是两端理解同一套数据格式
- `sync/` 层从「部分完成」升级为 **P0**——需在 P0 阶段走通手机→PC 的数据闭环
- `cross_device/` 的设备配对和桥接升级为 P1
- `automation_hub` 的同步 API 升级为 P0

### 2.5 功能优先级

#### P0：不做没法用

这些功能构成「管家+第二大脑」的最小闭环。

| # | 功能 | 说明 | 对应角色 |
|---|------|------|---------|
| 1 | **对话** | 能和 AI 聊天，AI 基于记忆和知识回答 | 管家 |
| 2 | **输入收口** | 浏览器/手动/语音输入→统一进收件箱 | 收件箱 |
| 3 | **记忆存取（全量）** | 记录对话+自动提取事实+行为日志 | 第二大脑 |
| 4 | **本地知识问答** | AI 能基于本地笔记/文件回答问题 | 第二大脑 |
| 5 | **行为日志采集** | 记录文件变动、浏览器访问、App 使用 | 第二大脑 |
| 6 | **自动整理** | 行为日志+对话→自动分类、标记、结构化 | 整理器 |
| 7 | **有限授权执行** | AI 在授权后可读写指定目录文件 | 执行器 |
| 8 | **数据归属本地** | 所有数据存本地，无后端可独立运行 | — |
| 9 | **手机伴侣** | 手机端可对话、收件、查记忆、收通知 | 管家 |
| 10 | **跨端同步** | 手机和 PC 数据一致，实体模型同构 | — |
| 11 | **实体契约** | `domain/models/` 定义统一对象合同 | — |
| 12 | **层边界约束** | ruff 规则禁止反向 import，防止架构退化 | — |

**P0 闭环验证场景：**
```
今天在 PC 上: 我跟思忆集说"帮我记一下，小李的项目下周截止"
        → 它存入记忆
        → 同时记录到行为日志
        → 自动整理到项目标签
明天在路上: 我打开手机问"小李的项目什么时候截止"
        → 手机从同步数据中查到记忆
        → 回答我
        → 同时手机拍了张照片，自动同步回 PC
```

#### P1：不做体验差

| # | 功能 | 说明 |
|---|------|------|
| 13 | **Judge + provider 路由** | 默认本地 AI，复杂任务路由到合适云端模型，降低成本 |
| 14 | **审计日志** | 记录 AI 执行的操作（谁、什么时间、做了什么） |
| 15 | **日志归档策略** | 6 个月原始日志自动归档/清理 |
| 16 | **设备配对流程** | QR + PIN 双通道配对，初期可手动配置 |
| 17 | **通知推送** | 手机收到 PC 端执行结果通知 |
| 18 | **测试覆盖率 ≥ 80%** | 核心模块单元测试+集成测试 |
| 19 | **桌面 Doctor** | 启动诊断、配置修复、崩溃恢复 |

#### P2：锦上添花

| # | 功能 | 说明 |
|---|------|------|
| 20 | 工作台 / Dashboard | 可视化概览和继续入口 |
| 21 | 桌宠 / 角色表现层 | 小问形象、Live2D、字幕层 |
| 22 | 可视化工作流编辑器 | 拖拽编排流程 |
| 23 | 开放插件市场 | 第三方能力扩展 |
| 24 | 技术雷达 / 自升级 | 自动感知技术变化 |
| 25 | 智能决策优化 | 多方案多维度对比 |
| 26 | 执行回滚 | 撤销已执行的操作 |
| 27 | 统一入口三类分流 | chat / execute / automate 三类目标入口 |

### 2.6 架构约束

基于以上决策，以下架构约束对所有后续设计和实现有效：

```
C1. 3 层架构 + 1 个特权层
    ┌──────────────────────┐
    │  表现层（Face）        │  PyQt6 UI / Android / 手机 PWA
    │  职责：排版、交互、状态  │  只通过 service_registry 访问下层
    ├──────────────────────┤
    │  AI 管家层（Brain）     │  ◄── 特权层，可访问任何层，其他层不可反向依赖它
    │  职责：路由、意图理解、   │
    │        记忆存取、任务执行 │
    ├──────────────────────┤
    │  能力执行层（Hands）    │  文件管理、工作流、MCP、同步引擎、插件
    │  职责：执行具体操作      │
    ├──────────────────────┤
    │  持久化层（Storage）    │  LocalDataStore / SQLite / ChromaDB / 文件系统
    │  职责：数据持久化        │  不依赖任何上层
    └──────────────────────┘

C2. 层边界强制
    - ai/client/ 是底层 HTTP 工具，不允许依赖 assistant/、services/ 等上层模块
    - memory/ 是第二大脑的持久层，不允许依赖 services/（当前存在反向依赖，需修复）
    - app_runtime/ 是组装层，不允许依赖 ui/
    - 以上由 ruff 规则强制检查

C3. 实体契约单一来源
    - 所有跨端实体（Note、Task、Memory 等）的定义在 domain/models/ 下，Pydantic BaseModel
    - sync/、integrations/automation_hub_client、automation_hub/ 都引用同一份定义
    - 不允许三端各自定义同一实体格式

C4. 本地优先，无后端可运行
    - P0 所有功能在纯本地环境必须跑通
    - automation_hub 只作为增强（同步、备份），不是运行时依赖
    - 启动时如果后端不可用，不影响对话、记忆、文件操作

C5. 行为日志隐私红线
    - 行为日志（文件操作、浏览器访问）默认标记为「仅本地」级别
    - 不经用户显式授权，不得发送到任何云端模型
    - 这是 Q1 有限授权原则的延伸

C6. DI 容器只做组装，不做门面
    - AppContext 负责服务实例化和生命周期，不暴露业务方法
    - 服务通过 service_registry.resolve() 获取
    - 按领域拆分 Context（AiContext、MemoryContext、ServiceContext 等）
```

### 2.7 对当前代码库的影响

按新 PRD 重新评估当前代码库的投入偏差：

| 子系统 | 代码量 | 按 PRD 优先级 | 实际投入 | 偏差 |
|--------|--------|--------------|---------|------|
| UI 层（mixin、样式、面板） | 最大 | P1 | 已投入最大精力 | **过度** |
| 工作台 / Dashboard | ~2,000 行 | P2 | 已完成 | **超前** |
| 桌宠 / 角色表现层 | ~500 行 | P2 | 已有实现 | **超前** |
| assistant/（Judge、autonomy 等） | ~6,000 行 | P0/P1 | 已完成 | 正常 |
| memory/ | ~6,800 行 | P0 | 已有但需扩展行为日志 | 正常，需增强 |
| sync/ + cross_device/ | ~2,700 行 | **P0** | 部分完成 | **滞后** |
| domain/models/ | 存根（~0 行） | **P0** | 空 | **严重滞后** |
| ai/client/ | ~1,500 行 | P0 | 已完成 | 正常 |
| data/ | ~800 行 | P0 | 已完成 | 正常 |
| automation_hub | ~20,000 行 | P0/P1 | 已完成 | 正常 |
| 行为日志采集 | **不存在** | **P0** | 不存在 | **缺失** |

**核心发现：当前投入最多的（UI、工作台、桌宠）恰好是 P2 功能，而 P0 的命门（domain/models、sync 接入、行为日志采集）恰好是最薄弱的环节。**

## 3. 替代方案

### QC-1 的替代选择

- **A（严格受控）**：每次执行前确认。安全但对话流碎片化，不符合「管家」体验。拒绝。
- **C（高度自治）**：AI 自行判断。与「数据归属本地」「隐私红线」原则冲突。拒绝。

### QC-2 的替代选择

- **A（仅对话记忆）**：实现简单，空间占用最小，但不符合「第二大脑」定位。拒绝。
- **B（对话+事实提取）**：合理的基础方案，但「全量记录」是第二大脑的本质特征，缺少行为日志意味着 AI 不知道你做了什么文件操作、浏览了什么内容。拒绝。

### QC-3 的替代选择

- **A（可有可无）**：与手机端已有投入不匹配。拒绝。
- **B（重要但不紧急）**：合理，但用户明确选择同步上线，尊重决策。拒绝。
