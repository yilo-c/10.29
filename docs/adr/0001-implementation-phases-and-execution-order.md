# ADR 0001: 修复路线与执行阶段

## 状态

已批准

## 日期

2026-05-06

## 依赖

- [ADR 0000](0000-product-requirements-and-architecture-direction.md) — 定义 P0/P1/P2 优先级

---

## 1. 背景

ADR 0000 固定了产品需求和功能优先级。经审计发现，当前代码库的投入分布与 PRD 优先级存在严重偏差：P2 功能（UI、工作台、桌宠）投入最大，而 P0 的基础设施（domain/models、sync 接入、行为日志采集）最薄弱。

本 ADR 定义修复的执行顺序。核心原则：**先建 P0 闭环，再做 P1/P2 打磨。不影响 P0 闭环的问题后置。**

---

## 2. 总路线

```
时间 ─────────────────────────────────────────────────────────────→

Phase 0          Phase 1              Phase 2              Phase 3
止血            建地基              通闭环               打磨
（3 天）         （7 天）             （5 天）              （持续）

层边界规则      实体契约            跨端同步验收          Judge 联调
retry 修复      行为日志采集        全量记忆闭环         审计日志
层环断开        sync 通道           有限授权执行         日志归档
文档路径走查    泛型化 client        P0 场景验收          测试覆盖率
                                   手机伴侣最小能力      UI 层收敛
                                                       DI 拆分（可选）
                                                       上帝类拆分（可选）
```

---

## 3. 各阶段详述

### Phase 0：止血

**目标：阻止新代码继续制造问题，修复现有 bug。**

不影响 P0 闭环，但后续阶段的安全前提。

| # | 任务 | 预估 | 影响文件 |
|---|------|------|---------|
| 0a | ruff 层边界规则 | 0.5 天 | ruff.toml |
| 0b | 修复 classify_error 不可达重试 | 0.5 天 | ai/client/base.py, ai/llm_resilience.py |
| 0c | 断开 P0 层环 | 1 天 | ai/client/fallback.py, memory/index.py |
| 0d | 文档路径走查 | 1 天 | docs/code-architecture-mapping.md, docs/refactoring-plan.md |

### Phase 1：建地基

**目标：建立 P0 功能的底层基础设施。**

这里产出的东西是 P0 的命门，但它们本身不直接面向用户。

| # | 任务 | 预估 | 说明 |
|---|------|------|------|
| 1a | **domain/models/ 实体契约** | 3 天 | Pydantic BaseModel 定义 Note、Task、Memory 等，这是 sync 和 memory 对齐的前提 |
| 1b | **行为日志采集器** | 2 天 | 文件变动监控 + 浏览器桥接 + App 状态，写入标准格式日志 |
| 1c | **跨端 sync 通道打通** | 1 天 | 泛型化 sync + automation_hub_client，验证手机→PC 单条数据流转 |
| 1d | **泛型化 integrations/automation_hub_client** | 1 天 | 796 行 → ~200 行，消除 6 实体 × `prepare_request/parse_response` 重复 |

### Phase 2：通闭环

**目标：跑通 P0 全部验证场景。**

按 ADR 0000 §2.5 的 P0 验证场景验收：

> 今天在 PC 上说「小李的项目下周截止」→ 存入记忆 → 记录到行为日志 → 自动整理
> 明天在手机上问「小李的项目什么时候截止」→ 从同步数据中查到 → 回答
> 手机拍了照片 → 自动同步回 PC

| # | 任务 | 预估 | 说明 |
|---|------|------|------|
| 2a | 手机伴侣最小能力 | 2 天 | 对话、收件、查记忆、收通知，使用已有 automation_hub + PWA |
| 2b | 全量记忆闭环 | 2 天 | 扩展 extractor 处理行为日志，验证记录→提取→检索链路 |
| 2c | 有限授权执行 | 1 天 | AI 读写指定目录文件，权限矩阵初版 |
| 2d | P0 验证场景通测 | — | 端到端走通，确认闭环成立 |

### Phase 3：打磨

**目标：按需补充 P1 功能，清理已知架构债务。**

这里不做大重构。按 ADR 0000 的 P1 优先级逐项补。

| # | 任务 | 预估 | 说明 |
|---|------|------|------|
| 3a | Judge + provider 路由 | 2 天 | 联调本地 AI + Judge + 云端 fallback |
| 3b | 审计日志 | 2 天 | 记录 AI 执行的操作 |
| 3c | 日志归档策略 | 1 天 | 6 个月原始日志自动归档/清理 |
| 3d | 测试覆盖率 ≥ 80% | 持续 | 核心模块补测试 |
| 3e | UI 层收敛 | 可选 | mixin→服务组合、3 层样式→property-only |
| 3f | DI 拆分 | 可选 | AppContext → 按领域 Context |
| 3g | 上帝类拆分 | 可选 | AutonomousAssistantManager 等 |

---

## 4. 不做（明确推迟）

以下事项在 Phase 3 完成后仍列为「不做」：

- P2 功能（Dashboard、桌宠、可视化工作流等）— 参见 ADR 0000 §2.5 P2 列表
- 完全自治（AI 自我修改代码）— ADR 0000 QC-1 排除
- 多租户/企业版 — ADR 0000 §2.1 排除
- 开放插件市场 — P2

---

## 5. 风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| domain/models 兼容现有 settings.json 格式 | 中 | Phase 1 延迟 | 先审计现有数据格式再定义 models |
| 行为日志采集影响系统性能 | 中 | 用户体验下降 | 异步写入 + 批处理 + 低优先级 I/O |
| 手机端需额外开发超出 PWA 能力 | 低 | Phase 2 延迟 | 第一阶段对齐 PWA 已有能力（已支持收件+查记忆），不新增原生开发 |
| AI 读写文件导致数据丢失 | 低 | 数据安全 | Phase 2c 权限矩阵限制目录范围，Phase 3b 审计日志记录操作 |
