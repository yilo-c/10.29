# AI 联网扩展安全设计

本文档承接 [ai-networked-extension-rules.md](ai-networked-extension-rules.md) 的产品规则，补安全层面的最小设计。

它回答的是：

1. AI 联网扩展最主要的风险是什么。
2. 哪些控制点必须存在。
3. 什么时候只能推荐，什么时候才能真正启用。

## 当前威胁模型

当前至少要防四类风险：

1. 来源污染：把不可信内容伪装成可信扩展或可信输入。
2. 权限扩大：低风险信息补充链路绕成高风险执行链路。
3. 状态失控：扩展失败、半安装、半启用后没有统一恢复路径。
4. 审计丢失：联网行为发生了，但用户或系统之后无法还原。

## 最小控制点

### 一、注册控制

- 新扩展来源必须先进入统一 registry
- 记录来源、权限、风险、健康和启停状态
- 不允许匿名来源直接成为默认可执行能力

### 二、权限控制

- 读取信息、产生建议、触发动作三层权限分开
- 高风险权限默认关闭
- UI 不得直接绕过安全层调用联网扩展

### 三、执行控制

- 所有联网扩展执行都应有 request/response 级别的基本留痕
- 失败路径要有统一错误类型与恢复提示
- 对外部内容的写入动作要么进入确认，要么进入审批或白名单

### 四、回滚控制

- 禁用某来源后，planner 不再选择它
- 安装失败、启用失败、升级失败都必须可回退
- 不允许出现“看似已关闭，但实际上仍在后台调用”的状态

## 当前放行标准

只有同时满足下面几项，某类联网扩展才算具备最小放行条件：

1. 来源可识别
2. 权限可解释
3. 风险可分级
4. 失败可恢复
5. 行为可审计

如果做不到，就只能作为“推荐能力”存在，不能作为默认启用的“安装能力”存在。

## 当前阶段建议

当前阶段最合理的安全策略是：

- 先把浏览器桥接、受控 provider、MCP 接入统一成受控来源
- 先做 registry、权限说明、失败诊断和回滚提示
- 后做安装、升级、商店和更多来源生态
