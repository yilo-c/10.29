# 决策：记忆衰减机制（T7.4 处置）

- 状态：已决策（2026-08-23）
- 决策人：项目唯一开发者（个人 agent 自评视角）
- 关联：评审报告 T7.4 / Phase 2 伴侣闭环
- 来源：依据 `deliverables/思忆集全栈评审报告-2026-08-23.md` §9.2/§11.3 修正后前提

## 1. 背景与问题

评审计划原文假设存在 `memory/layer.py` / `memory/scheduler.py` 的记忆衰减（遗忘曲线）机制，T2.4 任务为"补运行证据测试 + 图谱-MD 一致性巡检"。

**代码实证（2026-08-23）**：`memory/` 下**不存在任何 decay / forget / 衰减 / layer 权重机制**（grep 零命中）。真实检索语义是：

- `NarrativeInjector.get_recent_milestones` / `get_mood_trend`（`memory/narrative/narrative_injector.py`）：按时间倒序取最近 N 条，**无权重衰减**；
- `assistant_memory_index`（`memory/index.py`）：entries 只追加、软删无上限、无遗忘策略；
- 检索排序依赖 ChromaDB 相似度 + FTS，**无时间衰减因子**。

即：计划假设的"记忆衰减机制"是**不存在的虚构前提**。T7.4 应回答：**产品是否需要引入遗忘曲线/权重衰减？**

## 2. 决策

**当前阶段不引入记忆衰减机制，维持"时间倒序 + 语义检索"现状；以"数据增长上限"替代"遗忘"作为约束手段。**

具体拆分：

1. **不做**显式的遗忘曲线（如 Ebbinghaus 衰减、半衰期权重、定期 purge）。
2. **已确认的既有约束**：行为日志按 180 天保留（T5.3 已接线每日归档）；`assistant_memory_index` 为只追加软删，需靠 T5.2 备份 + 后续对**单键上限**治理（见 §4）控增长。
3. **检索排序**保持语义相关度优先；不引入时间衰减，避免"旧但重要"的记忆被系统性降权。

## 3. 理由

1. **产品价值**：个人第二大脑的核心理念是"可靠记住"，主动遗忘与产品定位相悖；"记太多"的实际风险是存储/检索性能，而非记忆污染（单人数据量级有限）。
2. **工程成本**：引入衰减需同时改 Chroma 排序因子、NarrativeStore 过滤、检索 API 签名，且要补一套"衰减可见性"测试——当前性价比低。
3. **已有替代约束**：T5.3 已解决行为日志无限增长；`assistant_memory_index` 的软删机制已能"标记失效"（revoke），配合检索排序天然弱化旧条目。
4. **唯一真实瓶颈**是 `assistant_memory_index` 单键无上限（`memory/index.py:666,578`）——这是**容量治理**问题，不是"遗忘"问题。

## 4. 影响与后续动作

- **立即**：无代码改动（决策即结论）。
- **跟进（容量治理，非衰减）**：若 `assistant_memory_index` 单键体积增长到可感知（如 >10MB），引入 `entries` 上限裁剪（保留最近 N + 软删条目按期清理），落点 `memory/index.py` 的 `_append_audit` 附近。
- **不做清单**：不引入时间衰减因子、不做定期记忆 purge、不改检索排序语义。
- **重开条件**：若未来出现"记忆污染干扰检索"的真实反馈（非性能），再评估按来源（source_type）做降权而非全局衰减。

## 5. 反证（如何证明"不做"是正确的）

- 运行 3 个月后 `assistant_memory_index` 体积仍在可接受范围（<10MB 目标），且 recall 精度无明显下降；
- 若体积超限，触发的是 §4 的**上限裁剪**而非遗忘曲线，证明"约束增长"路线有效。
