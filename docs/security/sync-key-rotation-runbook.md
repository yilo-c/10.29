# 思忆集 — 同步口令轮换 Runbook

**归属**：debt-sprint v2 TASK-V3-04（对应问题 C-2「同步口令无轮换 runbook」）
**适用范围**：E2E 同步口令（PBKDF2 派生的同步密钥，`sync/_cloud_sync_crypto.py`）
**对照文档**：[secret-management.md](secret-management.md)、[sync-protocol-design.md](../sync-protocol-design.md)

---

## 1. 背景：为什么要轮换

思忆集的跨设备同步用「同步口令」经 PBKDF2 派生加密密钥，对所有云端同步数据做
AES-256-GCM 端到端加密。Cloudflare Worker 只持有密文与校验和，看不到明文。

触发轮换的场景：
- 口令可能泄露（设备丢失 / 外泄平台登录 / 疑似钓鱼）。
- 安全策略要求的定期轮换（建议每 180 天）。
- 员工 / 家庭成员退出后不希望其继续解密历史同步数据。

> ⚠️ 口令**不是** Worker 侧的 `REGISTER_SECRET`（那是注册/吊销用的预共享密钥，
> 与数据加密无关）。本文档只讲**同步数据加密口令**的轮换。

---

## 2. 轮换前准备

1. 备份当前口令（写进团队密码库，仅轮换期间生效）。
2. 确认所有存活设备都**已登录**（能完成一次同步），否则轮换后离线设备将无法解密。
   - 停用的设备应先吊销其 token：`POST /api/sync/revoke-device`（V3-02）。
3. 确认 Worker 的 `MIN_CLIENT_VERSION`（V3-05）不低于当前最小可用客户端，
   否则旧客户端会拿到 `SYNC_VERSION_TOO_OLD` 而被拒——轮换不应成为强迫升级的工具。

---

## 3. 轮换流程

### 步骤 1：在「主设备」更换口令

打开设置 → 跨设备同步 → 「同步口令」，输入新口令并保存。
主设备立即用 PBKDF2 派生**新**密钥，并把所有待同步资源（notes/todos/settings）
以新密钥重新加密后推送到 Worker。

### 步骤 2：逐设备同步新口令

依次在各存活设备上把「本地同步口令」改为新口令 → 触发一次手动同步。
每台设备应看到：
- 上传：本机数据以新密钥重新加密推送（覆盖旧密文）。
- 下载：拉到的是其他设备以新密钥加密的数据，能正常解密。

> 旧口令未更新的设备，在切换前拉到的将是**新密钥加密的密文**，解不开 → 报
> 解密失败。这是预期信号，提醒该设备需要更新口令。

### 步骤 3：Worker 旧数据过期策略

Worker 侧 `sync_data` 按 `(device_id, resource)` 主键 `INSERT OR REPLACE` 覆盖，
因此只要每台设备都完成一次重推，云端不残留旧密钥密文。

为兜底清理长期未同步/已吊销设备留下的旧密文（它们无法被解密、只会占用空间），
可选执行（需管理员）：
- 在 D1 `sync_data` 上按 `updated_at` 清理超过 N 天的记录，或
- 删除指定已吊销 `device_id` 的全部 `sync_data` 行。

> V3-05 决策 b 说明：如果引入更高的 `MIN_CLIENT_VERSION`，应对低版本客户端返回
> 明确错误码而不是静默失败，避免「新旧混跑」解密混乱。

---

## 4. 验证

1. 新口令下新增一条数据 → 各设备同步后均可见且可解密。
2. 任一台设备撤销到旧口令 → 拉新数据报解密失败（验证确实换了钥）。
3. 恢复到新口令 → 正常。

---

## 5. 回退方案

仅当**新口令下出现不可恢复的解密失败**（如误掉设备、口令拼写导致部分设备丢失）时回退：

1. 用步骤 1 的备份口令在「主设备」恢复为新口令。
2. 让受影响设备重新填回**旧的备份口令**，手动同步。
3. 若某台设备已用新口令重推送数据，切换回旧口令后它反而解不开——所以**回退
   必须由主设备先行**，其他设备随后跟随，避免在主设备切回前先被旧密钥覆写。

> 第 2 步的「逐设备重新加密推送」在回退时同样成立：把「新口令」替换成「备份旧口令」，
> 其余步骤完全一致。
