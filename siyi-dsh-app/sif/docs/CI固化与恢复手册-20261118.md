# CI 固化与恢复手册（2026-11-18）

## 一、为什么必须做这一步

思忆集当前所有修复都落在两个**不在 APK 内**的位置：

```
/storage/emulated/0/思忆集/plugins/*.js     5 个用户插件
/storage/emulated/0/思忆集/app/sif/core/*   8 个核心模块
```

覆盖安装 APK 时：

- `EngineInstaller` 删除并重解压 `dsh-home`
- 用户插件目录虽在 `/sdcard`，但换机、清理存储、误删都会丢
- `sif/core` 完全靠手工维护

**累积的改动清单**（截至 2026-11-18）：

| 文件 | 大小 | 补丁标记 |
|---|---|---|
| siyi-vault.js | 42298B | PATHFIX / TITLEFIX / HTTPHARDEN / INDEX |
| siyi-vault-tools.js | 7741B | — |
| siyi-fallback.js | 7989B | — |
| siyi-quota.js | 29094B | — |
| siyi-permission-guide.js | 3055B | — |
| core/vault/*.mjs (5 个) | 34583B | — |
| core/bridge/*.mjs (3 个) | 20926B | — |

一旦丢失，前面所有工作归零。

## 二、固化包结构

```
sif/dist/
  manifest.json       文件清单 + sha256 + 补丁标记 + 版本
  checksums.txt       人类可读校验清单
  ci-embed.md         CI 集成说明
  plugins/            5 个插件
  core/vault/         5 个核心模块
  core/bridge/        3 个桥接模块
```

共 13 个文件，145682 字节。

## 三、三条命令

```bash
cd /storage/emulated/0/思忆集/app/sif

# 1. 生成/更新固化包（改完插件后跑）
node scripts/build-dist.mjs

# 2. 校验固化包与运行目录是否一致
node scripts/apply-dist.mjs --check

# 3. 部署（覆盖安装后恢复用）
node scripts/apply-dist.mjs --apply

# 4. 回滚到部署前
node scripts/apply-dist.mjs --restore
```

`--check` 退出码：0 表示完全一致，1 表示有差异。

## 四、恢复演练结果（已实测）

`tests/contract/dist-restore-drill.mjs` 模拟五个真实场景，13 项全部通过：

| 场景 | 验证内容 | 结果 |
|---|---|---|
| 1 空环境首次部署 | 模拟刚覆盖安装、插件全丢 | PASS |
| 2 覆盖用户修改 | 重新部署时自动备份旧版 | PASS |
| 3 从备份恢复 | 恢复到用户修改版本 | PASS |
| 4 损坏源文件 | hash 不符时拒绝部署 | PASS |
| 5 原子性 | 无临时文件残留 | PASS |

关键点：**部署前会校验源文件 hash**，源损坏就拒绝写入，不会把坏文件铺上去。

## 五、部署脚本的安全设计

1. **源文件校验**：部署前比对 `manifest.json` 的 sha256，不符即跳过
2. **目标备份**：覆盖前把旧文件复制到 `backups/dist/<时间戳>/`
3. **原子写入**：同目录临时文件 + rename，不留半文件
4. **写入后复验**：写完再算一次 hash，不符报错
5. **隔离测试支持**：`SIYI_DIST_TARGET_ROOT` 环境变量可指向临时目录

## 六、CI 集成（需要仓库操作）

详细步骤见 `dist/ci-embed.md`，核心四步：

1. 把 `sif-core/` 打进 `web-profile.zip` 的 `node_modules/@siyi/sif-core`
2. 把 5 个插件打进 `node_modules/dsh-user-plugins/bundled`
3. `EngineInstaller.kt` 安装时铺到 `/sdcard/思忆集/plugins/`（跳过已存在）
4. CI 加校验步骤，确认包内文件齐全

**注意**：当前 `siyi-vault-tools.js` 用绝对路径 import：

```js
import { createVaultService } from '/storage/emulated/0/思忆集/app/sif/core/vault/service.mjs'
```

固化进包后应改为 `@siyi/sif-core/vault/service.mjs`，或在部署脚本里建软链。

## 七、固化包的边界

**包含**：插件代码、核心模块、清单、CI 说明

**不包含**：
- 用户笔记数据（`/sdcard/思忆集/vault/`）
- 引擎配置（`cordis.patch.yml`）
- 凭据（`gateway.key`、`credentials.yaml`）
- 会话历史（`sessions/`）

测试 `dist-restore.test.mjs` 有专门断言验证固化包不含用户数据和密钥。

## 九、每次改插件后的标准流程

```bash
# 1. 改完插件，先跑测试
node tests/contract/run-all.mjs

# 2. 重新生成固化包
node scripts/build-dist.mjs

# 3. 校验一致性
node scripts/apply-dist.mjs --check

# 4. 部署到运行目录
node scripts/apply-dist.mjs --apply

# 5. 重启引擎
sh scripts/restart-engine.sh

# 6. 验证
sh scripts/post-restart-verify.sh
```

第 4 步在正常情况下是幂等的（内容相同也会重写，但 hash 一致）。

## 十、覆盖安装后的恢复流程

假设刚装了新 APK，插件全丢：

```bash
# 1. 确认丢失
node scripts/apply-dist.mjs --check
# 会报「未部署」

# 2. 恢复
node scripts/apply-dist.mjs --apply

# 3. 重启引擎
sh scripts/restart-engine.sh

# 4. 验证
sh scripts/post-restart-verify.sh
# 期望：已注册 6/6 个 vault 工具
```

注意：如果 APK 里的 `sif-core` 路径变了（比如改成 `@siyi/sif-core`），
需要先改插件的 import 路径再部署。这个耦合点必须记在 CI 文档里。

## 十一、长期建议

1. **尽快把 dist/ 推进仓库**。现在它只在手机上，换机就没了。
2. **CI 构建时自动跑 dist 校验**，防止仓库与设备漂移。
3. **把 146 项测试也进仓库**，作为回归门禁。
4. **绝对路径 import 改为包名**，消除设备路径耦合。
5. **考虑把 sif-core 独立成 npm 包**，供多端复用（Windows/Linux 宿主也要用）。
