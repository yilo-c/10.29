第 3 条测试实际在 vault 里写入了一篇 `CSRF-TEST-SHOULD-NOT-EXIST`。
已通过 `/siyi-vault/delete` 移入回收站清理，确认列表查询为 0 条。

**风险描述**：手机浏览器里打开的任何网页，理论上都能读取全部笔记、往库里写内容。
这是本机回环服务最容易忽略的攻击面——因为「只监听 127.0.0.1」被误认为已经安全。

## 二、改造内容

不改引擎、不加依赖，只在插件路由层加四道闸门。

### 闸门 1：Host 必须是回环地址

挡 DNS rebinding（恶意域名解析到 127.0.0.1 后绕过同源策略）。

```
127.0.0.1 ✓   localhost ✓   [::1] ✓   ::1 ✓
evil.com ✗    192.168.1.5 ✗   空 ✗
```

### 闸门 2：Origin 必须同源

- Origin 缺失 → 非浏览器客户端（curl/node），放行
- Origin 与 Host 同源 → 放行
- 跨站 Origin → 403 FORBIDDEN_ORIGIN

### 闸门 3：写操作必须 application/json

这是挡 CSRF 的核心。浏览器能用三种方式发起「简单请求」绕过预检：

```
text/plain                        → 415
application/x-www-form-urlencoded → 415
multipart/form-data               → 415
application/json                  → 通过（会触发预检，跨站拿不到 CORS 许可）
```

`upload` 额外允许 `image/*` 与 `application/octet-stream`。

### 闸门 4：写操作限流

同一 host + action 每分钟 60 次，超出返回 429 RATE_LIMITED。

### 附带：安全响应头

```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
```

## 六、防护边界（必须说清楚）

当前方案挡住的是**浏览器跨站攻击**：

- 恶意网页读取笔记 ✗
- 恶意网页写入笔记 ✗
- DNS rebinding ✗
- 表单 CSRF ✗

**没有**挡住的是：

- 本机其他 App 直接访问 127.0.0.1:3180 ✗（仍可读）
- 有 root/Shizuku 的进程 ✗
- 物理接触设备的人 ✗

要挡「本机其他进程」需要进程级认证（Unix socket + peer credentials，或每次启动的随机 token）。
这属于更大的改造，已在框架文档第 9 节列为目标，不在本轮范围。

**设计取舍说明**：没有强制本机客户端也带 token，因为笔记面板是浏览器同源页面，
强制 token 会引入「前端如何拿到 token」的新问题。当前选择是「挡住跨站，信任本机进程」。
