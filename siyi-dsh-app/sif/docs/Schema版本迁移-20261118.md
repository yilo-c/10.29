# Schema 版本迁移机制（L1 数据层）

日期：2026-11-18  
定位：补齐迁移架构里 L1 数据层的唯一缺口。

---

## 一、为什么需要这个

`frontmatter` 的 `schema` 字段是**数据契约版本号**。当前所有笔记都是 `schema: 1`。

如果未来要改字段结构（比如加 revision 向量、改 folder 语义、加同步元数据），
没有迁移机制会发生两件事：

1. **旧笔记被新代码按新结构解读** → 静默丢字段或误读
2. **新笔记被旧代码读** → 遇到不认识的字段可能崩溃或覆盖

这两件事都不会立刻报错，而是数据慢慢坏掉。这是最危险的失败模式。

---

## 二、设计原则

| 原则 | 含义 |
|---|---|
| 迁移是显式动作 | 不隐式触发，用户可控 |
| 每版一个纯函数 | `migrate(v) -> v+1`，可单独测试 |
| 迁移前必须备份 | 失败可回滚 |
| 迁移幂等 | 已迁移的跳过，重复跑无副作用 |
| 版本不认识就拒绝 | 不猜测、不降级解读 |

然后跑 `node scripts/schema-tool.mjs migrate`。

## 五、核心实现

### 5.1 版本读取

```js
readSchemaVersion({ schema: 1 })    // 1
readSchemaVersion({ schema: '2' })  // 2（字符串可转）
readSchemaVersion({})               // null（缺失）
readSchemaVersion({ schema: 1.5 })  // null（非整数）
```

### 5.2 迁移计划

```js
planMigration(1)   // { ok: true, reason: 'UP_TO_DATE', steps: [] }
planMigration(2)   // { ok: false, reason: 'NEWER_THAN_SUPPORTED' }
planMigration(null)// { ok: false, reason: 'MISSING_SCHEMA' }
planMigration(0)   // { ok: false, reason: 'NO_MIGRATION_PATH' }
```

**关键设计**：高版本拒绝降级解读。

如果手机上是新版本代码（CURRENT_SCHEMA=2）写了笔记，然后回退到旧版本（CURRENT_SCHEMA=1），
旧代码看到 `schema: 2` 会拒绝处理，而不是按 v1 猜测。这样不会静默破坏数据。

### 5.3 扫描范围

只统计**正式笔记**：

- 排除 `.siyi/`（回收站、元数据）
- 排除非 ULID 命名（如 `README.md`）

这条是实测踩出来的：第一版扫描把回收站里的 11 篇和 README 也算进去了，
得到 69 篇而不是 57 篇。

## 六、本轮修复的两个真实 bug

### bug 1：list() 不返回 schema 字段

普查时发现 57 篇全部显示「schema 缺失」，但文件里明明都有 `schema: 1`。

根因：`list()` 的返回结构只挑了 id/title/kind/tags/... 十几个字段，
**漏了 schema**。`get()` 返回完整 meta，所以只有 list 有问题。

修法：`list()` 返回值加 `schema: meta.schema ?? null`。

这个 bug 说明：**数据契约字段必须在所有读取路径都暴露**，否则无法做版本治理。

### bug 2：migrateMeta 对最新版本误报「已变更」

`planMigration(1)` 返回 `{ ok: true, steps: [] }`（空步骤），
但 `migrateMeta` 只在 `!plan.ok` 时提前返回，空 steps 会落到末尾返回 `changed: true`。

修法：显式判空

```js
if (plan.steps.length === 0) {
  return { meta, changed: false, from, to: from }
}
```

## 九、边界与已知限制

| 项 | 状态 |
|---|---|
| 单版本迁移 | ✅ 支持 |
| 多版本链式迁移（v1→v2→v3） | ✅ 支持（`steps` 是数组） |
| 迁移失败自动回滚 | ⚠️ 需手工从备份恢复，工具不自动 |
| 迁移事务性（全部成功或全部不动） | ❌ 未实现，逐文件处理 |
| 迁移进度显示 | ❌ 未实现 |
| 并发保护（迁移时禁止其他写入） | ❌ 未实现 |

**事务性是最值得补的**：如果迁移 100 篇，第 50 篇失败，前 49 篇已改，状态不一致。

当前缓解办法：迁移前 tar 整库，失败就整库恢复。
