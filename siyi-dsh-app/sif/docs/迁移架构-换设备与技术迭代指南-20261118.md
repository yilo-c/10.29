# 迁移架构：换设备与技术迭代指南

日期：2026-11-18  
适用：思忆集 SIF 框架  
目标：**换手机、换操作系统、换 DSH/Agent 技术栈时，哪些能直接带走，哪些要重写，怎么改最省事。**

本文不是跨平台实现方案（Windows/Linux 宿主本轮不做），而是**可迁移性的契约定义**。

---

## 一、核心原则：分三层看待迁移成本

判断一个东西能不能迁移，先问它属于哪一层：

| 层 | 内容 | 换设备 | 换技术栈 | 迁移成本 |
|---|---|---|---|---|
| **L1 数据层** | Markdown 笔记、frontmatter、附件 | 直接复制 | 不用改 | 零 |
| **L2 契约层** | 能力描述符、错误码、桥接协议、Vault 接口 | 直接复用 | 少量适配 | 低 |
| **L3 适配层** | 平台路径、IPC、权限、UI、宿主生命周期 | 需重写 | 需重写 | 高 |

**迁移的本质是：把尽可能多的东西从 L3 下沉到 L1/L2。**

本轮改造做的就是这件事——把路径从 L3（写死在源码）下沉到 L2（由环境注入）。

---

## 二、L1 数据层：完全可迁移

### 2.1 什么是真源

```
<dataRoot>/vault/
  2026/2026-11/<ULID>.md    每篇一个文件，frontmatter + Markdown
  assets/<sha256>.<ext>      图片，内容寻址
  .siyi/trash/               回收站
```

**真源只有 Markdown 文件。** 索引、缓存、图谱都是派生物，删了能重建。

### 2.2 换设备怎么迁

```bash
# 旧设备：备份
tar -czf siyi-vault-backup.tar.gz -C /storage/emulated/0/思忆集 vault

# 新设备：恢复
tar -xzf siyi-vault-backup.tar.gz -C <新dataRoot>
```

**不需要迁移**：索引、日志、会话缓存、`current-state.json`。

### 2.3 换技术栈怎么迁

不用迁。任何能读 Markdown 的系统都能接管。这是选择 Markdown 作真源的最大价值。

### 2.4 唯一需要注意的兼容点

frontmatter 的 `schema` 字段是版本号：

```yaml
schema: 1    # 当前版本
```

若未来改字段结构，必须：

1. 升 `schema` 版本
2. 提供迁移脚本（读 v1 写 v2）
3. 旧版本遇到新 schema 要**拒绝写入**而不是静默丢字段

这条目前**还没实现**，是已知缺口。

## 三、L2 契约层：可跨设备跨技术栈复用

### 3.1 四个契约文件

```
sif/contracts/
  capability-v1.schema.json   能力描述符（11 个必填字段）
  error-v1.json               15 个稳定错误码 + retryable/ambiguous 语义
  bridge-v1（代码内）          JSON-RPC 方法集与消息格式
  VaultService 接口（代码内）  search/get/create/update/trash/stats/reconcile
```

这些是**与平台无关的**。换到任何宿主，只要实现这四样，上层全部复用。

### 3.2 能力描述符的迁移价值

```json
{
  "specVersion": "siyi.capability/v1",
  "name": "vault.search",
  "risk": "read",
  "idempotent": true,
  "timeoutMs": 15000
}
```

同一份描述符可以投影成：

- DSH 工具（当前）
- MCP 工具（未来）
- OpenAI function calling（未来）
- CLI 子命令（未来）

**投影层各写各的，契约只有一份。**

### 3.3 已验证的投影差异

DSH 的 schema DSL 有自己的白名单（`string` 只允许 `type/enum/const`），不支持 `pattern/minimum/format`。

所以适配器必须剥离这些键。这个差异已经写在 `core/vault/capabilities.mjs` 的注释里，换宿主时要重新确认。

## 四、L3 适配层：换设备必须改的部分

### 4.1 路径（本轮已解决）

**改造前**（不可迁移）：

```js
import { createVaultService } from '/storage/emulated/0/思忆集/app/sif/core/vault/service.mjs'
```

三个问题：装 APK 后路径不存在、换设备前缀不同、无法由宿主注入。

**改造后**（可迁移）：

```js
const SIF_ROOT = process.env.SIYI_SIF_ROOT
  || '/storage/emulated/0/思忆集/app/sif'
const { createVaultService } = await import(SIF_ROOT + '/core/vault/service.mjs')
```

配套 `core/paths.mjs` 提供完整解析：

| 环境变量 | 作用 | 默认值 |
|---|---|---|
| `SIYI_SIF_ROOT` | 核心模块根目录 | `/storage/emulated/0/思忆集/app/sif` |
| `SIYI_DATA_ROOT` | 数据根 | `/storage/emulated/0/思忆集` |
| `SIYI_VAULT_ROOT` | 笔记目录 | `<dataRoot>/vault` |
| `SIYI_PLUGINS_DIR` | 插件目录 | `<dataRoot>/plugins` |

**显式环境变量无条件优先**，不做存在性检查。这样测试隔离、CI、换设备都能用。

已测：12 项路径测试全通过，含「复制到新目录后仍能解析核心模块」的换设备模拟。

### 4.2 需要重写的适配层清单

换到新设备/新平台时，这些必须重写：

| 项 | 当前 Android 实现 | 换平台要做什么 |
|---|---|---|
| 进程监督 | Kotlin `EngineController` + 看门狗 | 重写为 systemd / Task Scheduler / launchd |
| 引擎启动 | `setsid` + 孤儿进程 | 平台各自的守护方式 |
| IPC | 抽象命名空间 Unix socket | Windows Named Pipe / Linux 文件 socket |
| 系统权限 | Android 运行时权限 + 特殊权限 | 平台各自的权限模型 |
| 通知 | NotificationManager | Toast / libnotify |
| 日历 | CalendarContract | 平台 API 或 ICS 文件 |
| UI | WebView + 客户端插件 | 各自前端 |
| 文件路径 | `/storage/emulated/0` | XDG / `%LOCALAPPDATA%` |

**注意**：这张表里没有 `VaultService`、没有能力描述符、没有错误码——那些是 L2，不用重写。

### 4.3 插件加载机制的可迁移性

当前用户插件加载器（`dsh-user-plugins`）是 DSH 特有的。换技术栈时：

- 若新宿主支持 ESM 动态 import → 插件可直接复用
- 若不支持 → 需要写一层适配，但插件**内部逻辑**不用改（只要用 `SIYI_*` 环境变量而不是硬编码路径）

本轮改造后，插件对宿主的依赖只剩两个：

1. `ctx.tools.register(defineTool(...))` — DSH 契约
2. `process.env.SIYI_*` — 可移植

第 1 条是唯一的技术栈耦合点。

## 五、换 DSH 版本时怎么迁移

DSH 是官方项目，会持续升级。升级时的风险点：

### 5.1 高风险：内部实现依赖

历史踩过的坑：

| 依赖 | 后果 | 应对 |
|---|---|---|
| `@deepseek-ai/dsh-session` 双实例 | 翻译功能必失败（`Receiver must be an instance`） | CI 里做实例统一 |
| DSH schema DSL 白名单 | 工具注册静默失败 3/6 | 用真实 `defineTool` 测试 |
| `output.render(args, value)` 签名 | 模型看到错误输出 | 按真实签名写测试 |
| 客户端 CSS 类名 hash | 选择器失效 | 用 `[class$="_frame"]` 后缀匹配 |
| 插件 `apply()` 内变量声明顺序 | TDZ 崩溃，整个渠道包消失 | 桩 ctx 实跑 apply |

**共同点：这些问题都是「语法通过、加载成功，但运行时行为错」。**

### 5.2 升级检查清单

```bash
# 1. 升级前：记录当前基线
node tests/contract/run-all.mjs > baseline.txt

# 2. 升级后：重跑
node tests/contract/run-all.mjs > after.txt
diff baseline.txt after.txt

# 3. 关键验证（不能只看测试通过）
#    - 真实模型工具循环（E5）
#    - 插件日志确认 N/N 注册
#    - HTTP 端到端
```

### 5.3 证据等级纪律

| 等级 | 含义 | 能证明什么 |
|---|---|---|
| E1 | 语法检查 | 不会崩溃 |
| E2 | 单元/桩测试 | 逻辑正确 |
| E3 | 真实宿主校验器 | 契约对齐 |
| E4 | 真实宿主端到端 | 功能可用 |
| E5 | 真实模型完整回路 | **模型真的会用** |

**E2 全绿不能替代 E4/E5。** 本轮就吃过两次亏：

- 桩 `defineTool` 测 12 项全过，真实引擎只注册 3/6
- render 测试按错签名写断言，插件错了测试反绿

## 六、未来 Agent 技术迭代的适配策略

### 6.1 保持可替换的边界

```
┌─────────────────────────────────────────┐
│  Experience（UI / CLI）                  │  ← 可替换
├─────────────────────────────────────────┤
│  Agent Runtime（DSH / 未来方案）         │  ← 可替换
├─────────────────────────────────────────┤
│  Integration（工具注册 / 模型路由）       │  ← 薄适配层
├─────────────────────────────────────────┤
│  Domain（VaultService / 待办 / 索引）     │  ← 稳定，不随技术栈变
├─────────────────────────────────────────┤
│  Data（Markdown + frontmatter）          │  ← 最稳定
└─────────────────────────────────────────┘
```

**判断标准**：任何新技术的接入，改动应该只发生在上面两层。如果动到了 Domain 或 Data，说明抽象没做对。

### 6.2 模型层迭代

当前已有：

- 模型能力探测（上下文窗口、模态、工具支持）
- 按 `provider/model/能力类别` 统计健康度
- 错误分类 → 立即换路 / 累计换路
- 上下文预算与压缩

换新模型时只需要：

1. 加进模型目录
2. 跑一次能力探测（工具循环、图片、长上下文）
3. 更新健康度基线

**不需要改 VaultService、索引、UI。**

### 6.3 协议层迭代（如 MCP）

若未来接入 MCP：

```
外部 MCP server
      ↓
  Normalizer（转成 siyi.capability/v1）
      ↓
  统一 Registry（与 DSH 工具同一个）
```

关键约束：

- MCP server 独立权限域
- 输出大小与超时限制
- 工具命名空间含 server instance
- 单个 server 崩溃不影响本地工具

这些已写进框架规范 §6.3，但**尚未实现**。

## 七、迁移操作手册

### 7.1 换手机（同平台）

```bash
# 旧设备
cd /storage/emulated/0/思忆集
tar -czf /tmp/siyi-migrate.tar.gz vault plugins patches config

# 新设备（先装同版本 APK）
cd /storage/emulated/0/思忆集
tar -xzf /tmp/siyi-migrate.tar.gz

# 恢复固化包（保证插件是当前版本）
cd /storage/emulated/0/思忆集/app/sif
node scripts/apply-dist.mjs --apply
sh scripts/restart-engine.sh
sh scripts/post-restart-verify.sh
```

### 7.2 换 DSH 版本

```bash
# 1. 备份
tar -czf /tmp/siyi-pre-upgrade.tar.gz -C /storage/emulated/0/思忆集 vault plugins

# 2. 记录基线
cd /storage/emulated/0/思忆集/app/sif
node tests/contract/run-all.mjs > evidence/baseline-pre-upgrade.txt

# 3. 装新 APK

# 4. 恢复固化包
node scripts/apply-dist.mjs --check    # 会报不一致
node scripts/apply-dist.mjs --apply

# 5. 重跑测试
node tests/contract/run-all.mjs

# 6. 真实工具循环验证（E5）
#    新会话里让模型调 vault_search，确认输出正确
```

### 7.3 换操作系统（未实现，路线）

执行手册阶段 6B/6C 定义了最小切片：

```
supervisor CLI + IPC + status/echo/notify + vault CLI
```

但按当前决定**本轮不做**。若将来要做，顺序是：

1. 实现 `core/paths.mjs` 对应的平台默认值
2. 实现 IPC 传输层（Named Pipe / Unix socket）
3. 实现 supervisor
4. 复用 VaultService 与能力描述符
5. 跑同一套合同测试

## 九、一句话总结

**能迁移的是数据与契约，必须重写的是平台适配。**

本轮把路径从源码常量变成运行时注入，就是把这个边界往正确的方向推了一格。

判断未来任何一次技术迭代是否安全，只需要问一个问题：

> 这次改动动了 L1/L2，还是只动了 L3？

只动 L3，随便换；动了 L1/L2，必须写迁移脚本并跑全部证据等级。
