## 一、笔记编辑：关于「对标小米笔记」的诚实说明

### 1.1 我尝试了什么

为了不凭截图仿照，我做了三次一手资料获取：

| 尝试 | 结果 |
|---|---|
| 网上搜索小米笔记功能清单 | ❌ 百度/必应抓取失败（反爬 + VPN 干扰） |

APK 探测结果（真实数据）：

```
包名: com.miui.notes   路径: /data/app/~~EyAc.../base.apk
APK 大小: 96,103,593 字节（96MB）
```

**结论：我没能完整提取到小米笔记的功能清单。** 继续深挖的技术成本已经超过收益。

## 二、待办自动化：已改为可选

### 2.1 改动

**之前**（我上一版做错了）：AI 操作条直接放在待办页顶部，默认展开 —— 等于把自动化强加给所有任务。

**现在**：

```
[今日] [全部] [工作] [生活]  [🤖 AI]  ← 默认关闭的开关
                                    ↓ 点击后才展开
                                  [✨拆解目标] [🗓安排今日] [🧹清理积压]
```

- 开关默认关闭，不占用视觉空间
- 只有用户主动点开、再点具体功能，才会调用 AI
- 普通待办（记下来就完事）完全不受影响

### 2.2 你举的场景已实现：定时抓取偏好新闻

新增 `lib/newsScheduler.ts`：

```ts
scheduleDailyFetch({ enabled: true, time: '08:00', regions: ['cn','intl'] })
```

- 用 `LocalNotifications` 注册每日重复通知（`on: {hour, minute}, repeats: true`）
- 系统托管，App 被划掉也能准时弹出
- 配置持久化在 localStorage，跨启动保留
- 记录 `lastRunDate`，避免重复抓取

**为什么不用后台静默抓取**：Android 后台限制严格，长期后台任务需要前台服务 + 常驻通知，耗电且会被小米省电策略杀掉。用「到点通知 → 用户点开 → 抓取」更务实，可达性也更高。

## 四、【重点分析】AnyClaw 与 DSH 安卓版

> 本节**未改动任何源码**，仅分析。

### 4.1 先厘清三个东西

| 名称 | 是什么 | 与本项目关系 |
|---|---|---|
| **AnyClaw** | 你现在手机上的宿主 App（`gptos.intelligence.assistant`），提供 host-bridge 能力（am/bsh/termux-*、相机、通知、剪贴板等） | 是**容器/运行时**，不是 agent 内核 |
| **DSH** | DeepSeek Harness，约 120 个 npm 包的 agent 框架（`@deepseek-ai/dsh@0.1.0-rc.6`） | 是 **agent 内核**，跑在 Node 上 |
| **思忆集** | 你的项目，Electron + Python 后端 + Capacitor 手机端 | 是**数据 + 功能壳** |

### 4.2 仓库里已有一份高质量调研

`docs/dsh-integration-report-2026-08-15.md`（2026-08-15，基于 DSH 源码一手阅读）。核心结论：

> **推荐结合，方向正确；但换的是「内核」，不是「壳」。**
>
> 1. "玩具感"的主要来源是**自建 agent 内核**（butler/judge/react_engine/多 agent 编排），而不是数据功能缺失。
> 2. DSH 的能力矩阵几乎逐条覆盖你缺的东西（持久会话、goal、子代理、工作流、调度、技能、MCP、沙箱审批）。
> 3. 推荐 = 思忆集瘦身为「个人数据 + 功能路径」并暴露 MCP Server，DSH 作为独立执行内核。

**关键证据**：报告第 187 行明确写：

> **移动端/跨设备**：手机端走思忆集 WS 的路径可保留（**DSH 无需上手机**）；若未来要手机直连 agent，再评估 DSH headless 包装为远程服务。

### 4.3 回答你的问题：能做「DSH 安卓版」吗？

**技术上可行，但不该是当前目标。** 分三层说清楚：

#### 层一：DSH 跑在 Android 上 — 可行但难受

DSH 是 Node.js 框架。Android 上跑 Node 的现实路径：

| 方式 | 可行性 | 问题 |
|---|---|---|
| Termux 装 Node | ✅ 可行 | 需用户手动装 Termux + Node，非 App 形态 |
| 打包 Node 进 APK（nodejs-mobile） | ⚠️ 勉强 | 原生库兼容问题多，包体积 +30MB，维护成本高 |
| 改写为纯 Kotlin/JNI | ❌ 不现实 | 等于重写整个 DSH |

**核心矛盾**：DSH 的价值在于「成熟内核 + 生态」，一旦为 Android 重写就失去这个价值。

#### 层二：你真正想要的可能是「手机上有个强 agent」— 已有更优解

AnyClaw 现在就能给你：`bsh`（宿主侧 Java 执行）、`am`（Activity 管理）、`termux-*`（相机/通知/剪贴板/震动/TTS）。**这套能力已经是"手机上的执行层"**，缺的是调度它的智能内核。

#### 层三：推荐架构（与 DSH 报告一致，但补上手机侧）

```
┌─ 手机 (Android) ─────────────┐        ┌─ 桌面 / 云端 ──────────┐
│ 思忆集手机端 (Capacitor)      │        │ DSH (Node, agent 内核) │
│  ├ 数据 UI（笔记/待办/资讯）  │◄──WS──►│  ├ 持久会话 / goal     │
│  ├ SiyiNative（17+ 原生能力） │        │  ├ 子代理(codex/claude)│
│  └ httpFetch（本次新增）      │        │  ├ 调度 / 技能 / MCP   │
│                              │        │  └ 沙箱 / 审批         │
│ AnyClaw host-bridge          │        └───────────┬────────────┘
│  (bsh / am / termux-*)       │                    │ MCP
└──────────────────────────────┘        ┌───────────▼────────────┐
                                        │ 思忆集 Python 后端      │
                                        │ (数据服务 + MCP Server) │
                                        └────────────────────────┘
```

**分工**：
- **手机**：数据采集 + UI + 原生能力执行（拍照、通知、无障碍、悬浮球）
- **DSH**：思考、规划、调度、调用子代理
- **Python 后端**：数据持久化 + 对外暴露 MCP 工具

手机不需要跑 DSH，只需要**能发任务、收结果**。这已经是当前 `rpcClient` 在做的事。

### 4.4 向 AnyClaw 靠近 vs 向 DSH 靠近 — 我的判断

你说「更偏向 DSH 的安卓版」，我理解你的真实意图是：**希望这个 App 有 DSH 那样的智能程度，同时是手机原生的**。

这两件事不冲突，但要分清「能力」和「形态」：

| 维度 | 现状 | 建议 |
|---|---|---|
| **智能内核** | 自建，反复推倒（报告证实） | **借 DSH**，不重造 |
| **手机形态** | Capacitor App（已成型） | **保留**，这是资产不是包袱 |
| **原生能力** | 17 个方法 + AnyClaw bridge | **继续扩展**，这是差异化 |
| **数据层** | Python + SQLite（成熟） | **保留**，改造成 MCP Server |

**结论：不要做「DSH 的安卓移植版」，要做「DSH 驱动的安卓 App」。**

前者是重写内核（4 个月实践已证明会变玩具），后者是换个更聪明的后端。

### 4.5 如果确实要做，最小可行路径

按 DSH 报告的分阶段，加上手机侧：

| 阶段 | 内容 | 工作量 |
|---|---|---|
| S0 | 冻结 `automation_hub`/PyQt6/桌宠/扩展 | 1 周 |
| S1 | 思忆集瘦身为数据服务 | 2-3 周 |
| S2 | 写 MCP Server（Python FastMCP） | 1-2 周 |
| S3 | DSH 自定义 profile + 每日资讯技能 | 1 周 |
| **S4** | **手机端接 DSH api-gateway**（替代现有 WS） | 1-2 周 |

S4 是关键：手机端 `rpcClient` 从「连 Python 后端」改为「连 DSH api-gateway」，UI 几乎不用改。
